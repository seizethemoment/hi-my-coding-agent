# 08. 第七步：安全与审批

## 本步目标

把“能执行”升级成“可控执行”。

coding agent 不是普通聊天机器人，它会：

- 读代码
- 改代码
- 跑命令

所以安全边界不能靠用户自觉，必须落在代码结构里。

## 本步交付

- `src/safety/commandPolicy.ts`
- `src/safety/approval.ts`
- `src/safety/outputLimit.ts`

## 第一版最低要有哪些安全能力

### 1. 工作区边界

只允许访问当前工作区内的文件。

### 2. 命令策略

先做最基础版本：

- denylist
- 超时
- 输出截断

### 3. 审批机制

建议第一版至少对 `bash` 做审批。

用户体验可以很朴素，比如：

- 打印命令
- 询问 `y/n`

先别追求 fancy UI。

## 为什么审批要独立成层

不要把审批写死在 `bash.ts` 里面。

更合理的结构是：

- 工具执行器只声明“我要执行什么”
- 审批层决定“是否允许执行”

这样未来：

- 自动批准某些命令
- 项目级白名单
- CI 模式禁交互

都比较容易扩展。

## 第一版建议阻断哪些东西

至少要非常谨慎对待：

- 删除类命令
- `sudo`
- 关机 / 重启
- 网络下载执行
- 改工作区外文件

注意：

denylist 不是完整安全方案，但第一版必须先有。

## 本步验收标准

完成后至少要做到：

1. 危险命令会被拒绝或要求审批
2. 批准前不会真正执行 shell
3. 路径逃逸被拦住
4. 超长输出不会把 CLI 和日志打爆

## 常见坑

### 1. 以为“有 denylist 就安全了”

不是。denylist 只是第一道粗网。

### 2. 审批逻辑散落在每个工具里

未来非常难统一。

### 3. 把安全看成“后面再补”

到了这一步已经不能再拖。

## 和业界产品的对应关系

- `Cline`：强调每一步审批
- `Claude Code` / `Codex`：强调 sandbox 和权限模式
- `Cursor Background Agents`：官方文档明确提醒自动跑命令会带来数据外泄风险

所以本教程也必须把安全提升到架构层。
