# 06. 第五步：做可交互 CLI

## 本步目标

把前面的 agent loop 接到一个能真实使用的终端界面里。

到这一步，用户才能像使用真正的 coding agent 一样操作它。

## 本步交付

- `src/cli/repl.ts`
- `src/cli/render.ts`
- `src/cli/commands.ts`

## 第一版 CLI 应该有多简单

第一版不要追求炫。

只要具备：

- 输入一条消息
- 显示模型回复
- 显示工具执行
- 支持几个基础 slash commands

就够了。

## 推荐先做的命令

- `/help`
- `/clear`
- `/quit`
- `/model`

如果这一版还没做多模型切换，`/model` 可以先只打印当前模型。

## 终端展示要分三类输出

### 1. 用户输入

清楚标识出是谁发的消息。

### 2. assistant 文本

支持逐字或逐段流式打印。

### 3. 工具事件

至少显示：

- 工具名
- 关键参数
- 成功 / 失败
- 结果摘要

这样日志可读性会高很多。

## 第一版要不要上 TUI 框架

不建议。

理由：

- 第五步的目标是交互闭环，不是复杂界面
- Node 自带 `readline` 就够用
- 等第一个版本稳定，再考虑 `ink`、`blessed`、自研 renderer

## CLI 和 agent loop 的边界

CLI 只负责：

- 接收用户输入
- 调用 agent
- 展示事件

CLI 不要负责：

- 拼装消息历史
- 执行工具
- 直接访问 provider API

这些边界越清楚，后面做测试越轻松。

## 本步验收标准

完成后至少要做到：

1. 启动 CLI 后可以连续输入多条消息
2. assistant 回复能显示
3. 工具执行过程能显示
4. `/quit` 能退出
5. `Ctrl+C` 的行为明确，不会把终端弄乱

## 常见坑

### 1. CLI 直接持有太多业务状态

会导致后面无法做 session resume 和测试。

### 2. 流式输出和最终结果重复打印

流式和最终消息要设计清楚，否则终端会重复刷屏。

### 3. 工具输出原样无上限打印

大输出必须截断。

## 参考项目里的启发

- `Aider`：终端体验非常朴素，但足够高效
- `pi`：交互态消息展示层次清楚
- 微信那篇 `Mini-Claude`：先做 CLI，再慢慢增强渲染，是对的
